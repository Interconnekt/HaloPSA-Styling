## 1. Priority one: ship the Cloudflare Worker

**Status: unblocked.** DNS for `interconnekt.com.au` is now in
Cloudflare, which was the only thing standing in the way.

The runbook already exists and is current: `Portal/email-iframe-theming.md`,
section "Recommended path: Cloudflare Worker". It has the architecture
diagram, the complete Worker source (about 20 lines using
`HTMLRewriter`), the `content-type` safety net, the rollback path and
the costs. Do not redesign it; implement what is written.

### What the Worker unlocks

`Portal/iframe-theme.js` is a finished, tested shim that has never run
in production, because there is no way to get a `<script>` into the
HaloPSA self-service portal without it. Six features are sitting behind
it:

| # | Feature | Why CSS cannot do it |
|---|---|---|
| 1 | Email body theming (Figtree, `#3355D8` links) | Content is inside `iframe.halo-html-renderer`; CSS does not cross a document boundary, even same-origin |
| 2 | Fixed-width email overflow containment | Same. Added 2026-09-02, verified by injection: content 4407px to 642px on ticket 358840 |
| 3 | `Age` column formatting on the ticket list | HaloPSA renders a raw float (`154.31099186313773`); needs JS to format |
| 4 | Status-chip class stamping | Pills ship with no class hook |
| 5 | Priority-pill class stamping | Same |
| 6 | On-hold indicator stamping | The string "On Hold" ships with no class hook |

Feature 3 is worth calling out: the raw float is visible to customers
on `/portal/tickets` right now and looks like a bug, because it is one.

### Also decide: does the Worker take over CSS delivery?

Joel's note is that the Worker removes the GitHub Pages delay. It can,
and this is a real decision rather than a detail.

Today the portal loads the stylesheet via an `@import` in HaloPSA's
Custom CSS field, pointing at GitHub Pages, which serves
`cache-control: max-age=600`. Consequences observed repeatedly last
session: after a merge the CSS is live within about a minute, but any
browser that already has it keeps the old copy for up to ten minutes.
Several "it is still broken" reports were this and nothing else.

Three options, in the order I would consider them:

1. **Proxy the asset through the Worker** and set a shorter TTL, or a
   `stale-while-revalidate`. Keeps CSS in the document head, so no
   flash of unstyled content, and kills the ten minute lag. Lowest
   risk.
2. **Serve the CSS from Workers KV**, deployed by a GitHub Action on
   merge. Removes GitHub Pages from the path entirely. More moving
   parts, and a second place the file can be stale.
3. **Inject the CSS with the script.** Do not do this. The stylesheet
   is 350KB and would arrive after first paint, so every page would
   flash unstyled.

Option 1 unless there is a reason not to.

### Verification, because the last session got burned on this

After deploying, confirm the script actually lands and runs:

```bash
curl -s https://portal.interconnekt.com.au/portal/tickets \
  | grep -c 'iframe-theme.js'
```

Then in a browser, on a ticket with a forwarded marketing email
(`/portal/ticket?btn=45&viewid=1&id=358840` is the known case),
check the email body reflows rather than clipping. And on
`/portal/tickets`, check the `Age` column shows a formatted value
rather than `154.31099186313773`.

If the script loads but nothing changes, the likely cause is the SPA
replacing DOM after the script ran. `iframe-theme.js` already installs
a `MutationObserver` for this; read it before assuming it is broken.

Be honest about these rather than assuming they work.

**Mobile has never been rendered.** Not once, in any session. The
browser tooling available here resizes the Chrome window but the tab's
`innerWidth` stays pinned at 1800, so every responsive decision made so
far was reasoned from reading the cascade, not seen. Everything
width-dependent is inside `@media (min-width: 769px)` so it cannot
reach mobile, but that is a containment strategy, not proof.

Specifically worth a real device:
- The ticket detail toolbar below 769px still uses HaloPSA's float
  layout. The three-different-baselines problem that was fixed on
  desktop exists there too.
- The KB sidebar `top: 190px` override is desktop-only by design; check
  the mobile stacked layout still looks right.
- The sticky back button (`top: 68px`) is desktop-only for the same
  reason.

**The Tile split pane has never been exercised.** `.portal-ticket-splitter`
renders the same ticket-detail component under a container whose
padding is deliberately zeroed. Every column-geometry rule carries
`:not(:has(.portal-ticket-splitter))` as a guard, but no one has opened
that view, because reaching it means changing a saved view preference
on an impersonated customer contact. Switch a real account to Tile view
and look.

## 5. Outside this repo

**The 2026 brand assets cannot be hotlinked.**
`https://interconnekt.com.au/brand/2026/...` is served with
`cross-origin-resource-policy: same-site`, so a browser refuses the
resource from any cross-site document. `curl` returns 200 and Chrome
renders a broken image, which makes it look like a working URL.

`docs/reference/brand-assets.md` in the Website repo names those URLs
as the definitive reference "for email signatures, partner
directories, press kits, Slack, anywhere that needs a URL". All of
those are cross-site, so the documented contract does not hold in a
browser. This reaches well past this repo.

Fix is a `cross-origin` CORP value for that path in the Website repo.
Until then, `PDF-Templates/_brand/` holds a local copy for the mockups,
with the reason recorded in its README. If CORP is relaxed, delete that
directory and point the mockups back at the canonical URLs.

**Two stale worktrees** hold their own uncommitted copies of the KB PDF
template: `kb-pdf-design-c87ce6` and `halo-billing-table-layout-7c5c2b`.
Both are superseded by what is on `main` (the normalised version). They
are Joel's uncommitted files so nothing has touched them, but they will
conflict if those branches are ever merged.

## 7. How to work in this repo without breaking it

Four traps, each of which caused a shipped regression last session.

**1. HaloPSA reuses class names across structurally different pages.**
This is the big one. Three regressions came from it.

- `.main-tile-item` is the stacked ticket Tile view AND the
  side-by-side service catalogue.
- `.svcatalog-item` is the catalogue item list AND, with `.varheight`,
  the category picker, which has a completely different DOM.
- `.details-group.card-panel` and `.details-group-header.title` are the
  read-only ticket sidebar AND the New Ticket form.

Before writing a selector, check whether the class appears elsewhere in
a different structure, and scope to something that only the target page
has. Then prove it: load the other page and count matches.

**2. Find which rule is responsible by testing, not reasoning.** The
reliable technique, because the cascade here is four stylesheets deep
with `!important` on both sides:

```js
const css = await fetch('https://interconnekt.github.io/HaloPSA-Styling/Portal/self-service-portal-design.css',
  {cache:'no-store'}).then(r=>r.text());
const body = css.replace(/\/\*[\s\S]*?\*\//g,'');
const el = document.querySelector('YOUR_SELECTOR');
const re = /([^{}]+)\{([^{}]*)\}/g; let m;
while ((m = re.exec(body))) { const s = m[1].trim(); if (s.startsWith('@')) continue;
  try { if (el.matches(s)) console.log(s, '|', m[2].replace(/\s+/g,' ').slice(0,100)); } catch(e){} }
```

To see how a page is meant to look, disable our stylesheet and measure
in a **separate** tool call:

```js
for (const sh of document.styleSheets) { let rs; try { rs = sh.cssRules } catch(e) { continue }
  for (const r of rs) if (r.type === 3 && r.href && r.href.includes('self-service-portal-design')) sh.disabled = true; }
```

Do not combine that with `await requestAnimationFrame` in the same
call, and do not use `adoptedStyleSheets` with the full stylesheet.
Both froze the renderer.

**3. Injecting a rule to test it does not mean it shipped.** One fix
last session was verified by injection, reported as done, and never
written to the file. After deploying, re-check against the deployed
stylesheet, not against your own injected copy.

**4. The ten minute cache.** GitHub Pages serves the stylesheet with
`max-age=600`. After a merge the file is live in about a minute but
browsers hold the old one. Several "still broken" reports were only
this. Check the server with `curl` before believing the browser. The
Worker work in section 1 can remove this.

### House rules

- **No em dashes (U+2014) or en dashes (U+2013)** anywhere: code,
  comments, commit messages, PR bodies. Verify with
  `grep -rnP '\x{2014}|\x{2013}'`.
- Australian spelling in prose.
- Use the existing tokens. Never hardcode a hex that has one. The
  `:root` and `.theme-dark` blocks at the top of the stylesheet are the
  full list, and `Interconnekt/Design-System` `tokens/tokens.json` is
  the upstream authority.
- Merging to `main` IS the deploy. GitHub Pages serves from `main` at
  root, so a merge puts CSS in front of customers within a minute.
- Push with the explicit refspec:
  `git push origin HEAD:refs/heads/<branch>`.
- The portal login is an impersonated customer contact. Do not change
  saved preferences (theme, list view), do not submit forms, and do not
  click Pay, Submit, Add Note or Time Entry.
